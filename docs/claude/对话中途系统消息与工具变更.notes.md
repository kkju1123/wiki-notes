# 对话中途系统消息与工具变更

*原文: [https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages) · 来源: web · 生成时间: 2026-09-20T03:05:35.949101+00:00*

## 背景

Claude API 的 prompt caching 会按 tools → system → messages 顺序对请求前缀做哈希，命中要求前缀字节完全一致到缓存断点。顶层 system 和 tools 位于前缀最前面，一旦修改就会让整段会话缓存全部失效。长 agentic 任务需要在运行中追加策略、权限或工具变更，重新处理全部历史会造成更高的延迟和成本，因此需要一种不破坏前缀的动态控制方式。

## 痛点

开发者如果直接改顶层 system 或 tools 数组来调整后期策略/工具，会让每轮都错过缓存，整段历史被重复处理。若把系统级约束放到 user 消息，虽然能传达指令，但系统指令的优先级和权威性不足，用户输入可能覆盖这些约束。

## 解决办法

核心做法是把后期变化追加为 messages 数组中的 role: system 消息；顶层 system 与 tools 数组保持稳定，缓存前缀不变，下一请求仍命中缓存。工具变更则先在顶层 tools 声明完整工具集，通过 system 消息 content 中的 tool_addition/tool_removal 块引用已声明工具来开放或撤回能力；需要初始隐藏的工具可声明 defer_loading: true。系统消息仍具备运营方优先级，冲突时后发 system 覆盖先发，中途 system 覆盖顶层 system。可以类比为 append-only 日志：不改历史，只在末尾追加状态变更。

## 关键代码示例

```javascript
const payload = {
  model: 'claude-sonnet-4-5',
  system: 'You are an agent.',
  tools: [
    { name: 'get_weather', input_schema: { type: 'object' } },
    { name: 'run_sql', input_schema: { type: 'object' }, defer_loading: true }
  ],
  messages: [
    { role: 'user', content: '先看天气' },
    { role: 'assistant', content: '工具结果...' },
    { role: 'system', content: [
        { type: 'tool_removal', tool: { type: 'tool_reference', name: 'get_weather' } },
        { type: 'tool_addition', tool: { type: 'tool_reference', name: 'run_sql' } },
        { type: 'text', text: 'From now on, all SQL must be parameterized.' }
    ] },
    { role: 'user', content: '查一下用户表' }
  ],
  betas: ['mid-conversation-tool-changes-2026-07-01']
}
```

这段示例把顶层 system 与 tools 数组固定下来：run_sql 带 defer_loading: true，所以初始不暴露给模型。执行到中间轮次时，追加一条 role=system 消息，content 中的 tool_removal 撤回 get_weather，tool_addition 开放 run_sql，并用 text 块写入系统级约束。由于顶层 tools/system 字节未变，缓存前缀仍与之前一致，后续请求继续命中缓存。

## 关键流程

1. 把全局长期不变的指令留在顶层 system，所有可能需要工具都声明在 tools 数组；默认不开放的工具加 defer_loading: true。
2. 在对话中需要变更的位置追加 role: system 消息，不要编辑顶层 system 或 tools。
3. 工具变更时，在该 system 消息的 content 数组里放 tool_addition 和/或 tool_removal 块，用 tool_reference 引用已声明工具；MCP 工具用 mcp_tool_reference 或 mcp_toolset_reference。
4. 如果需要同时写入新的系统约束，用同一条 system 消息的 text 块表达，例如“从现在起 SQL 必须参数化”。
5. 使用工具变更能力时携带 beta header：mid-conversation-tool-changes-2026-07-01。
6. 冲突规则：后发 system 覆盖先发 system，中途 system 覆盖顶层 system；确保临时约束确实按预期生效。

## 关键点

- prompt caching 请求前缀按 tools → system → messages 顺序哈希，修改最前面的 tools 或顶层 system 会改变前缀哈希，使整段缓存失效；这是本特性的直接动因。
- 中途 system 消息追加在消息历史末尾，不影响已缓存的前缀，因此后续请求仍能命中缓存，同时保留系统级优先级。
- 工具变更不修改 tools 数组，而是通过 system 消息的 tool_addition/tool_removal 块引用已声明工具；defer_loading: true 可实现最小权限。
- 系统消息与用户消息的任务不同：system 来自应用运营方，user 来自终端用户，冲突时系统优先；因此安全/策略约束应使用 system 角色。
- 该机制特别适合长会话中的策略切换、权限授予、用户插话注入和每轮提醒，避免上下文无限堆积。

## 对比与权衡

- 相比直接修改顶层 system：中途 system 在缓存友好上更好，几乎不增加历史重算成本；但只适用于从某一点开始生效的增量指令，全局永久指令仍应放顶层 system。
- 相比把指令放进 user 消息：system 消息在优先级和权威性上更好，能防止终端用户通过提示冲突覆盖；但 user 消息更轻量，不应把所有普通交互都包装成 system。
- 相比运行时直接增删 tools 数组：tool_addition/removal + defer_loading 在缓存稳定性上更好，但要求预先在 tools 声明所有可能能力，且该能力目前处于 beta。

## 自测问题

**问: 为什么顶层 system 只改一句话也会让整段缓存全部失效？**

缓存是对前缀做哈希，严格按 tools → system → messages 顺序；命中要求到缓存断点的每个字节完全一致。顶层 system 位于前缀第二段，任何改变都会生成新哈希，后续已缓存消息全部无法复用。因此变更应从中间追加，而不是改开头。

**问: tool_addition / tool_removal 为什么不会破坏缓存？**

它们位于 messages 数组某条 system 消息的 content 里，而缓存断点通常在前面的 tools/system 处。顶层 tools 数组未改变，前缀哈希一致，旧缓存仍能命中；工具可见性只是从该消息往后逻辑上变化。

**问: defer_loading: true 与一开始不在 tools 里声明有什么区别？**

不声明则无法被 tool_reference 引用，引用会返回 400 tool_reference_unresolved；声明但 defer_loading: true 表示工具存在于顶层集合中，但模型初始看不到，只有 tool_addition 后才会提供。这实现最小权限并在不修改前缀的前提下动态开放能力。

**问: system 消息和用户输入的指令冲突时，模型应该听谁的？**

system 代表应用运营方，user 代表终端用户；冲突时系统指令优先级更高。同一角色内部，后发 system 覆盖先发 system，中途 system 覆盖顶层 system。因此安全策略应写在中途 system 中，避免被用户覆盖。

**问: 什么时候不该用中途 system 消息？**

如果指令从会话一开始就确定且不再变化，应放顶层 system；不频繁变化的工具集也直接放顶层 tools。只在后期才出现、或想避免改动前缀时才用中途注入。还要注意工具变更目前需要 beta header，并有 pause turn 后的额外限制。

## 适用场景

- 长 agentic 会话中途切换模式或策略，例如从“探索代码”切换为“执行写操作”，新的系统约束从当前轮生效。
- 危险工具按需授权：初始用 defer_loading 隐藏 SQL/支付等工具，用户确认或流程进入审批后才 tool_addition 开放，结束后 tool_removal 撤回。
- 用户中途输入但上一轮工具循环仍在进行：将用户新请求作为 system 消息插入到工具结果之后，让 agent 合并处理而非打断。
- 每轮注入短暂提醒（剩余 token、文件变更、截止时间）而不让历史消息堆积，提醒只对当前轮/后续轮生效。
