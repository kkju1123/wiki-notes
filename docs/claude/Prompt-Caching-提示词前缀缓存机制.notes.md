# Prompt Caching：提示词前缀缓存机制

*原文: [https://platform.claude.com/docs/en/build-with-claude/prompt-caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) · 来源: web · 生成时间: 2026-09-20T03:02:49.355809+00:00*

## 背景

LLM 推理是自回归的，每个 token 生成时都要基于前缀计算注意力。对于多轮对话、few-shot 示例等场景，大量相同前缀被反复处理，浪费算力。Prompt caching 把前缀的 KV 状态缓存到服务端，后续请求可直接复用，从而减少重复计算。

## 痛点

没有缓存时，每次 API 请求都要对完整 prompt 从头做 prefill，即使系统提示词和历史对话基本不变，也会重复消耗时间和 token 费用。多轮 agent 或长上下文应用会因此延迟高、成本不可控。

## 解决办法

在请求中通过 cache_control 标记缓存断点，系统会缓存断点前所有可缓存内容的内部表示（主要是 prefill 阶段产生的 KV cache）。后续请求若前缀相同则直接命中缓存，跳过这部分 prefill，只需为新后缀计算。缓存按写入价、读取价计费，读取价约为基础输入价格的 0.1 倍。提供两种模式：自动缓存（顶层字段，断点随对话增长自动后移）和显式断点（块级控制，最多 4 个断点）。

## 关键代码示例

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    # 显式断点：系统提示词几乎不变，单独缓存
    system=[
        {
            "type": "text",
            "text": "你是一名资深后端工程师，回答需给出原理和工程权衡。",
            "cache_control": {"type": "ephemeral"}
        }
    ],
    messages=[
        {"role": "user", "content": "解释一下 PostgreSQL 的 MVCC"},
        {"role": "assistant", "content": "MVCC 通过隐藏行版本和事务快照..."},
        {"role": "user", "content": "它和 InnoDB 的 MVCC 有什么区别？"}
    ],
    # 自动缓存：顶层字段，断点自动落在最后一个可缓存块
    cache_control={"type": "ephemeral"}
)

```

system 块上的 cache_control 是显式断点，适合缓存长期不变的指令；顶层 cache_control 启用自动缓存，系统会把断点自动放在最后一个可缓存块（如最新用户消息），使历史对话前缀得以复用。实际请求中两种方式可共存，自动缓存占用 4 个断点槽之一。

## 关键流程

1. 在请求中通过 cache_control 标记缓存断点（显式或自动）。
2. 系统检查该断点之前的前缀是否在 TTL 内已缓存。
3. 若命中缓存，跳过该前缀的 prefill 计算，直接复用服务端 KV 状态。
4. 若未命中，正常处理完整 prompt，并在响应开始后写入前缀缓存。
5. 后续相同前缀请求自动命中；缓存每次命中会刷新 TTL，不额外收取读取费用。

## 关键点

- 缓存的对象是前缀对应的注意力内部状态（KV cache），而不是纯文本，这是它能跳过重复 prefill 计算的根本原因。
- 缓存断点必须遵循内容顺序，且系统会缓存断点之前连续的可缓存块，乱序或不可缓存内容会导致缓存失败。
- 自动缓存把断点动态放在最后一个可缓存块，适合多轮对话；显式断点适合控制变化频率不同的部分，但要注意最多 4 个断点和块顺序。
- TTL 从请求开始写入或读取缓存时计时，而不是响应结束后，长响应会显著消耗缓存有效期，需要据此设计重试间隔。
- 写缓存价格约为基础输入价的 1.25 倍，读缓存仅为基础输入价的 0.1 倍，因此重复前缀越多越划算。
- 缓存需要前缀达到最小 token 门槛（通常约 1024 token）才有明显收益，小前缀的缓存开销可能大于收益。

## 对比与权衡

- 相比本地拼接前缀，Prompt caching 在避免重复 prefill 计算上更好，但在实现复杂度和服务端依赖上不如本地管理透明。
- 相比语义缓存/向量检索缓存，Prompt caching 在结果确定性上更好，但在模糊匹配灵活性上不如语义缓存。
- 相比自动缓存，显式断点在缓存粒度控制上更好，但在配置简便性上不如自动缓存。
- 相比 5 分钟 TTL，1 小时 TTL 在长会话命中率上更好，但在写入成本上更高。

## 自测问题

**问: Prompt caching 的原理是什么？为什么能同时降低延迟和成本？**

自回归 LLM 推理分 prefill 和 decode。prefill 阶段对 prompt 前缀做注意力计算得到 KV cache，后续 token 生成依赖这些 KV。如果前缀相同，这部分 KV 可以复用。提示词缓存就是服务端把断点前内容的 KV cache 持久化，后续请求命中后跳过 prefill，既省计算时间也按更低的缓存读取价计费。

**问: 自动缓存和显式缓存断点怎么选？**

多轮对话中前缀不断增长但历史部分不变，适合自动缓存，系统自动把断点后移到最新可缓存块。如果不同内容块变化频率不同，例如 system 很少改但 tools 偶尔改，用显式断点可分别控制缓存边界。两者可以组合，但自动缓存会占用一个断点槽，总数通常为 4 个。

**问: 为什么缓存写入比普通输入 token 贵，而缓存读取那么便宜？**

写入需要正常 prefill 计算并把 KV 状态写入缓存，有额外的存储和管理成本；读取只是查表和复用已计算的 KV，因此便宜。对于重复前缀足够多的场景，多花约 25% 的写入价换取后续 90% 的读取折扣是划算的。

**问: TTL 为什么从请求开始时算，而不是响应结束？**

因为缓存生命周期需要限制内存占用，以请求开始时间统一计时简单且对服务端友好。这也意味着流式响应过长会消耗 TTL，因此如果响应可能要 4 分钟，后续复用必须在响应完成后约 1 分钟内发起，否则缓存过期。

**问: 启用 Prompt caching 后一定省钱吗？**

不一定。只有当相同前缀达到一定 token 长度且重复命中次数足够时，写缓存额外成本才能被读缓存的折扣覆盖。通常需要前缀至少约 1024 token 且有 2 次以上复用才划算。对于短 agent 固定指令但每次只有几十 token，缓存的节省可能不明显。

## 适用场景

- 多轮对话的 Chatbot 或 Agent，历史消息不断增长，自动缓存可以持续复用历史前缀。
- Few-shot 示例很长且每个请求都包含相同示例，把示例段用显式断点缓存。
- 固定系统提示词 + 大量工具定义 + 用户输入的场景，可以分别缓存系统提示词和工具定义。
- 长文档问答、代码库问询，先缓存文档内容，后续多次提问复用。
