# 云沙箱环境配置

*原文: [https://platform.claude.com/docs/en/managed-agents/environments](https://platform.claude.com/docs/en/managed-agents/environments) · 来源: web · 生成时间: 2026-09-20T07:21:44.409881+00:00*

## 背景

托管 Agent 运行代码需要可复现且隔离的 Linux 环境，若每次会话都从零配置会重复且易漂移。云沙箱环境把依赖包、网络策略等抽成模板，类似 Docker 镜像与容器实例分离：同一模板可被多个会话引用，但每个会话获得独立的运行实例。

## 痛点

没有环境模板时，每个会话都要重复声明依赖与网络规则，容易不一致；如果多会话共享同一文件系统，还会互相污染。网络策略如果管不到包管理器或 MCP 流量，可能导致安装失败或安全敞口。

## 解决办法

Environment 保存包清单和出网策略，创建会话时平台依据它启动全新 Linux 容器。包安装按包管理器字母顺序执行并跨会话缓存，但运行时文件系统完全隔离；网络限制作用于沙箱出口，limited 模式用 allowed_hosts 白名单，并用 allow_package_managers / allow_mcp_servers 两个独立开关放行公共 registry 与 MCP 端点，避免误伤。

## 关键代码示例

```json
{
  "type": "cloud",
  "name": "python-analysis-env",
  "packages": {
    "apt": ["graphviz"],
    "pip": ["sqlalchemy==2.0.30", "pandas"]
  },
  "networking": {
    "mode": "limited",
    "allowed_hosts": ["api.example.com", "*.internal.example.com"],
    "allow_package_managers": true,
    "allow_mcp_servers": false
  }
}
```

这段配置声明了一个 cloud 环境：apt 和 pip 分别预装系统与 Python 包，并固定 SQLAlchemy 版本；网络使用 limited 模式，只允许访问指定域名和通配子域。allow_package_managers 显式为 true，确保预装包能访问公共 registry。创建 session 时只需引用该环境 ID，平台就会按此模板生成独立容器。

## 关键流程

1. 创建 environment，填写 type: cloud 和唯一且描述性的 name。
2. 在 packages 中声明 apt/pip/npm 等依赖，并按需固定版本。
3. 配置 networking：unrestricted 为默认全放行；limited 则设置 allowed_hosts 白名单。
4. 若 limited 且声明了 packages，必须将 allow_package_managers 设为 true，否则请求以 400 被拒。
5. 创建 session 时传入该 environment ID，平台启动独立沙箱容器并完成预装。
6. 环境持续存在直到归档/删除；如需追溯变更，自行维护配置记录。

## 关键点

- 环境是模板，不是运行实例；每次 session 创建 fresh Linux container，多个会话不会共享文件系统。
- 包缓存跨同环境会话复用，可以显著降低冷启动时间，但它缓存的是包下载/安装产物，不是会话数据。
- 固定依赖版本是生产实践；unpinned 包会随时间变化，导致不可复现。
- 包管理器按字母顺序执行，这让安装顺序可预测，但不能替代跨语言依赖编排。
- networking 只控制沙箱内部进程的出站访问，web_search/web_fetch 由平台工具执行，需要另一套域名策略。
- limited 网络下的包管理器/MCP 开关是独立授权，只把域名加入 allowed_hosts 不够，必须显式打开。

## 对比与权衡

- 相比 self-hosted sandboxes，cloud environments 在免运维、平台安全补丁和弹性容量上更好，但在自定义网络拓扑、合规隔离和数据驻留控制上不如自托管。
- 相比每次创建 session 时内联依赖配置，environment 模板在一致性和复用性上更好，但当前不版本化，频繁变更时审计能力不如 Git 等版本化配置。
- 相比在沙箱启动后执行自定义 setup 脚本，packages 字段在可读性、缓存和平台托管上更好，但表达复杂初始化逻辑（如编译非标准依赖、生成配置）上不如脚本灵活。

## 自测问题

**问: 多会话共享 environment 时，文件系统为什么是隔离的？**

Environment 是配置模板，session 启动时基于模板创建新容器。包缓存可共享以加速，但容器根文件系统是每个 session 独立的，避免状态污染。类比 Docker image 与 container 的关系。

**问: limited networking 下已经 allowed_hosts 配置了 pypi.org，为什么还需要 allow_package_managers=true？**

平台把包管理器访问公共 registry 视为单独权限，不会仅因域名在 allowed_hosts 内就隐式授权，否则会被 400 拒绝。这样避免把“域名能通”等同于“允许包安装”，也便于统一控制供应链。

**问: web_search 和 web_fetch 的域名限制和 sandbox networking 是一回事吗？**

不是。沙箱 networking 控制 agent 在容器内的进程出网；web_search/web_fetch 跑在平台服务端。要限制工具访问的站点，应在 agent toolset 对应工具条目设置 allowed_domains/blocked_domains。

**问: 环境更新后，正在运行的 session 会受影响吗？**

不会。环境只在 session 创建时被读取并实例化，已运行容器不会热更新。因此新配置需要新建 session 才会生效；环境不版本化，变更记录需要团队自行保存。

**问: 为什么建议固定 packages 版本？**

未固定会安装 latest，导致不同时间的沙箱依赖不同，出现不可复现问题。生产环境应像 lockfile 一样 pin 版本，必要时结合哈希校验。

## 适用场景

- 同一类 agent 任务需要统一运行环境，例如 Python 数据分析、Node 前端构建。
- 频繁创建会话且依赖较多，需要利用包缓存减少启动延迟。
- 需要把沙箱出网限制在白名单域名的安全敏感场景。
- 并行运行多个互不干扰的任务，但希望共享同一依赖配置。
