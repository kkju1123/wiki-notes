# 会话预算：按公开列表价强制的硬性花费上限

*原文: [https://platform.claude.com/docs/en/managed-agents/budgets](https://platform.claude.com/docs/en/managed-agents/budgets) · 来源: web · 生成时间: 2026-09-20T07:34:30.382299+00:00*

## 背景

托管 Agent 会话可能长时间运行、并发多个线程并频繁调用工具，费用难以预估。传统的 max_tokens 只限制单次请求，无法约束整个会话的全额成本。Session budget 因此引入总花费护栏，让团队按会话设置硬上限。

## 痛点

没有预算时，一个失控的 agent 循环或多个并发线程可能在很短时间内产生高额账单。仅靠事后监控或告警无法阻止已经开始的消费。不懂硬预算的边界，如可略超、需要更新恢复，会导致误判为计费错误或设计出无法恢复的预算。

## 解决办法

在创建会话时传入 budget 对象，amount 用美分字符串避免浮点误差。平台按公开列表价持续计算 list cost，包括模型 token、web search 和会话运行时长。每次模型请求前检查累计成本，达到上限后不再发起新请求，但在途请求会完成，因此最终可能略超。会话进入 idle 且 stop_reason=budget_reached，保留历史与沙箱；修改或移除预算后自动恢复。更新预算必须大于已消费 list cost，而不是旧上限。

## 关键代码示例

```python
session_payload = {
    "agent_id": "agent-...",
    "budget": {
        "type": "limit",
        "max_list_cost": {"amount": "125", "currency": "USD"}  # $1.25
    }
}

# 达到预算后恢复：必须基于 usage.list_cost，而不是旧 max_list_cost
resume_payload = {
    "budget": {
        "type": "limit",
        "max_list_cost": {"amount": "130", "currency": "USD"}  # 假设已消费约 $1.253
    }
}

# 移除预算：JSON null 会移除上限并自动恢复会话
remove_payload = {"budget": None}
```

这段 payload 展示了创建和恢复预算的关键字段：创建时通过 budget.max_list_cost.amount 设置美分字符串，避免使用浮点数金额；恢复时新值必须基于会话当前 usage.list_cost，所以示例用 130 美分而不是旧上限 125 美分。移除预算时传 null，会话的暂停工作会自动恢复。

## 关键流程

1. 创建会话时设置 budget 字段，type 固定为 limit，金额使用美分字符串表示。
2. 平台持续累计 list cost：模型 token、web search、会话运行时长。
3. 每次模型请求前检查成本，达到上限时各线程在下一请求前暂停，在途请求完成。
4. 达到预算的会话进入 idle，stop_reason=budget_reached，保留历史与沙箱。
5. 通过 session update 提高、降低或移除预算；新值必须大于 consumed list cost，会话自动恢复。

## 关键点

- 预算只能在创建会话时附加，已有会话不能补加，因为它需要从会话开始就完整累计成本。
- amount 使用美分字符串而不是浮点数，避免 JSON 数字在二进制浮点下的舍入误差，保证金额精确。
- 执法发生在模型请求之间而非请求内部，因此预算是一个“新工作边界”而不是精确停止点，设计上限时必须预留一个请求的余量。
- 达到预算的会话是 idle 而非 terminated，事件顺序为 thread_status_idle -> session.usage -> session.status_idle，便于监控和恢复。
- list cost 按公开列表价而不是合同价计算，所以达到上限时实际账单可能更低；应把预算理解为控制信号而非最终账单。
- 更新预算必须大于 usage.list_cost 而非旧 max_list_cost，因为会话暂停时可能已经略超旧上限。

## 对比与权衡

- 相比单次调用的 max_tokens，session budget 控制整个会话跨线程、跨工具调用的累计花费，但不能阻止单个超大请求在暂停前完整执行，因此仍可能有一个请求的瞬时超限。
- 相比软预算或告警机制，session budget 会自动停止新工作，能真正防止费用继续累积，但可能中断正在进行的多步任务，需要人工或程序化调整预算恢复。
- 相比按合同折扣价计算预算，按公开 list price 计算更统一、平台侧更可预测，但会让客户更早触达预算护栏，实际扣费可能低于显示上限。

## 自测问题

**问: 为什么 amount 必须写成字符串而不是 number？**

金额用最小货币单位整数表示并用字符串传输，避免 JSON number 的二进制浮点误差。例如 0.1 + 0.2 在浮点数下并不精确，而计费金额不能有偏差。金融系统通常用整数或字符串承载金额。

**问: 会话达到预算后为什么 list_cost 会略高于 max_list_cost？**

因为检查发生在每个新模型请求之前，已经开始的请求不会被中断；每个线程最多一个在途请求超限，所以超出量有界。应把预算视为停止新工作的护栏，而非精确断点。

**问: 已经有一个没预算的会话，能否直接给它加预算？**

不能，API 返回 400。预算需要从会话生命周期开始持续累计，中途附加无法覆盖已经发生的成本；要么创建新会话，要么用外部监控方案。

**问: 会话暂停在 budget_reached 后，给它发 user.message 会怎样？如何恢复？**

user.message 会开始新工作，因此被拒绝 400；只接受 tool_confirmation、tool_result 等结算事件。恢复方式是更新 budget，新 max_list_cost 必须大于 usage.list_cost，或传 null 移除预算。

**问: list cost 和客户实际账单是什么关系？**

list cost 是按公开列表价算出的成本，用于统一执法；如果客户有谈判折扣，实际账单可能低于 list cost。会话在 list cost 达到预算时暂停，因此最终账单可能低于上限。

## 适用场景

- 面向客户的 agent 产品，需要给每个用户会话设置成本上限，防止恶意或失控使用。
- 长时间运行的多线程研究或编码 agent，总 token 和工具调用费用不可预测，需要总预算护栏。
- 通过 Deployments 批量启动会话时，对每个会话套用相同预算，实现统一成本控制。
- 需要在预算耗尽后自动暂停任务、保留沙箱现场，等待人工追加预算后继续的场景。
