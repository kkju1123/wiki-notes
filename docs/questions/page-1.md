# Questions · 第 1 页

## Q1: 什么是 TCP 三次握手？

三次握手是 TCP 建立可靠连接的过程：
1. 客户端发送 SYN=1, seq=x，进入 SYN_SENT；
2. 服务端回复 SYN=1, ACK=1, seq=y, ack=x+1，进入 SYN_RCVD；
3. 客户端发送 ACK=1, seq=x+1, ack=y+1，双方进入 ESTABLISHED。
核心作用：同步双方初始序列号、确认双方收发能力、防止旧重复连接被错误建立。
常见追问：为什么不是两次？两次无法确认客户端接收能力，且旧 SYN 可能让服务端单方面建立连接。为什么不是四次？四次多余，三次已经完成双向确认。


## Q2: 讲讲 Python 的 GIL 是什么，有什么影响？

GIL 是 CPython 解释器的全局解释器锁，保证同一时刻只有一个线程执行 Python 字节码。
影响：CPU 密集型多线程无法利用多核，甚至因线程切换更慢；IO 密集型多线程仍有效，因为等待 IO 时会释放 GIL。
存在原因：CPython 内存管理和对象引用计数需要线程安全，GIL 实现简单且兼容大量 C 扩展。
应对方案：CPU 密集型用 multiprocessing 多进程；IO 密集型用线程或 asyncio；也可用 C 扩展在耗时计算中主动释放 GIL，或考虑其他解释器/自由线程版本。

## Q3: ReAct与Plan-and-Execute架构差异及业务选型逻辑？

ReAct 是“思考-行动-观察”交替进行，每步根据环境反馈决定下一步，适合探索性强、步骤不固定、依赖中间结果的任务；Plan-and-Execute 先生成完整计划再逐步执行，适合流程较稳定、步骤可提前拆解的任务。业务选型看任务结构化程度、失败成本和延迟要求：结构化高、可并行、需要审计用 P&E；不确定性高、需要动态调整用 ReAct。实践中常混合：外层用 P&E 做稳定编排，子任务用 ReAct 处理局部不确定性。P&E 的缺点是计划错误时修正成本高，ReAct 缺点是 token 消耗高且容易跑偏。


## Q4: 模型、工具、状态在Agent中的核心分工？

模型是决策中枢，负责理解目标、推理、拆解任务、选择工具并生成参数；工具是执行层，负责与外部系统/数据交互，必须把结果和状态结构化返回；状态是运行期记忆，保存目标、已完成步骤、关键事实、约束和中间结果。清晰分工的原则是：模型不直接改外部世界，工具不替模型做高层决策，状态不参与推理但为推理提供上下文。这样设计便于权限控制、审计、缓存和故障隔离。


## Q5: 复杂任务为何不能只靠Prompt？何时需要工作流约束？

复杂任务不能只靠 Prompt，因为 Prompt 本质是非结构化约束，模型容易遗漏、顺序错乱、无法保证分支/重试/终止，长 Prompt 还会有注意力稀释问题。当任务包含多个有依赖的步骤、需要可靠分支、重试、超时、权限、审计或跨系统协同时，就应该用工作流约束。工作流提供确定性骨架，把关键路径和执行顺序固化，模型只负责局部语义理解、抽取、生成等非结构化环节。这样既保证可靠性，也便于监控、降级和人工介入。


## Q6: 单/多Agent如何选型？Agent数量越多性能越好吗？

单 Agent 适合任务边界清晰、工具少、上下文可控、延迟和成本敏感的场景；多 Agent 适合需要角色隔离、领域知识独立、并行执行、权限分级或复杂协作的场景。Agent 数量不是越多越好：多 Agent 会增加通信开销、协调成本、上下文传递误差、调试难度和延迟，整体效果可能更差。选型先看任务能否自然拆分为高内聚低耦合的角色/流程，再看是否真的需要独立记忆和权限；能单不轻易多，多 Agent 必须明确通信协议、状态边界和 Owner。


## Q7: 如何解决Agent工具循环调用、逻辑死循环问题？

先设置硬性预算：最大步数、最大耗时、最长无进展步数，超过即熔断或转人工。其次做循环检测：对连续相同或相似的 action/参数进行去重，若工具结果没有带来信息增益，就要求模型改变策略或终止。可以在 Prompt 和状态中强制写入“终止条件”和“失败条件”，工具返回统一包含状态码、是否完成、下一步建议。更可控的做法是用有限状态机或工作流约束工具序列，禁止任意循环；最后保留人工兜底和审计日志。


## Q8: 高危操作场景，如何设计HITL人工确认机制？

按风险分级：低风险自动执行，中风险事后审计，高风险必须 HITL。高危工具在执行前先由 Agent 生成“操作票”，包含动作、参数、影响范围、预期结果和回滚方案，渲染成可读表单给人工审批；审批支持批准、拒绝、修改，并记录审批人和时间。技术上把人工确认做成工具调用的前置阻塞步骤，而不是让模型自行决定是否确认；同时设置确认超时自动取消、操作窗口和二次验证。所有高危操作要可审计、可回滚，必要时在沙箱或 dry-run 模式下先预览。


## Q9: Function Calling与模型直出JSON的优劣及适用场景？

Function Calling 由模型/平台按工具 schema 生成结构化调用，工具选择和多参数约束更可靠，接入多工具、流式调用更方便；缺点是<mark>依赖模型和网关支持，调试和跨模型迁移略受限</mark>。直出 JSON 的优势是灵活、模型无关，适合简单结构化提取、非工具调用、离线或需自定义解析的场景；缺点是 schema 遵循不稳定，需要自己做校验、重试和错误处理。生产环境多工具调用优先 Function Calling；只做结构化输出或不方便走 FC 时用 JSON，但必须有校验层。


## Q10: 工具Schema设计要点，参数模糊会引发哪些线上问题？

工具 Schema 设计要站在模型的视角：名称用清晰的动词+名词，description 写清“什么时候用、做什么、有什么副作用、不做什么”，参数要定义类型、枚举、必填/可选、默认值、格式、约束和示例。参数模糊会导致模型臆造参数、调用错工具、漏填必填、枚举越界、格式错误，进而频繁重试、token 浪费，甚至误触发高风险操作。建议给枚举和默认值、少用开放字符串，工具数量多时分组和加路由说明。错误码也要结构化，便于模型自我纠正。


## Q11: 多相似工具场景，如何保证模型精准调用？

优先考虑合并：如果多个工具只是参数或数据源不同，抽象成一个工具，用枚举或参数区分。无法合并时，在 description 中明确适用条件、差异和反例，并在系统 Prompt 中给工具选择规则。可以在工具调用前增加轻量意图分类/路由，先粗筛候选工具，减少模型选择困难；对高风险或歧义场景，让模型先输出工具选择理由，再做最终调用。调用后校验参数和结果，不一致时自动纠错或询问用户。


## Q12: 工具调用失败，重试、熔断、降级方案如何设计？

先对失败分类：参数错误、业务拒绝、超时、限流、系统故障。参数错误和业务拒绝通常不应盲目重试，应让模型修正参数或终止；瞬时故障可用指数退避重试，设上限并保证幂等。熔断按错误率/慢调用比例触发，打开后快速失败，冷却后进入半开试探。降级策略包括切换备用工具、走缓存/默认策略、降级为只读或转人工。全链路记录失败原因、重试次数和最终状态，方便归因和优化。


## Q13: 工具持续超时，如何抉择等待、切换或终止任务？

工具持续超时先判断是偶发慢还是资源耗尽：结合历史耗时、下游状态和当前 QPS。短期可做一次快速重试或预检；如果 SLA 允许且任务关键，转为异步等待+轮询；有等效替代工具时立即切换。不可替代且已超过 deadline，应终止任务并返回可解释失败，避免继续占用 Agent 和下游资源。连续超时要触发熔断，限制后续调用，同时通知下游 owner。关键是设置合理的超时时间、最大等待时间和总任务 deadline。


## Q14: 如何规避Agent误调用高危工具的风险？

规避误调用核心是“权限最小化 + 防御性设计”。高危工具默认不暴露给模型，或在独立工具组中按风险分级授权；schema 中明确前置条件、副作用和禁止场景。调用前用规则引擎/策略层校验参数与业务规则，例如金额上限、目标资源、操作时间窗；敏感操作要求 dry-run 或 HITL。调用后记录完整审计，支持回滚。还可以在系统 Prompt 中设置安全边界和反例，限制高危工具只在特定上下文中可调用，必要时绕过模型由确定性规则执行。


## Q15: Agent状态存储边界是什么？为何不能全量存储对话？

Agent 状态存储的边界应以“任务完成所需的最小上下文”为原则，区分短期工作状态、会话级临时信息、长期用户事实和偏好。不能全量存储对话，因为原始对话会带入大量噪音、无关历史，导致 Token 膨胀、注意力稀释、检索质量下降，还存在隐私合规风险。通常只把关键事实、决策、约束、当前进度和必要的最近对话放入状态，其余按保留策略归档。这样做能控制成本和延迟，也便于审计和遗忘机制。


## Q16: 长短记忆的区别及对应适配业务数据？

短期记忆用于当前任务执行，包括最近的对话、工具返回、中间推理和未完成步骤，存在上下文或 Redis 中，任务结束即失效或压缩。长期记忆是跨会话持久化的用户画像、偏好、事实、历史决策和经验，存在数据库、向量库或知识图谱中。业务上，短期记忆适配临时流程和会话内追问；长期记忆适配个性化推荐、客户信息、历史工单、用户偏好等。长期记忆需要更新、冲突消解和过期机制，避免陈旧信息污染决策。


## Q17: 对话过长、Token溢出的解决方案？

核心思路是控制进入模型上下文的长度，而不是无限拼接历史。可采用滑动窗口保留最近 N 轮，较远历史做摘要或提取关键事实/状态；对长对话按主题切分并做 RAG 按需检索。设置上下文预算，每轮动态裁剪最不相关的内容，保留目标、约束、最近工具结果和用户偏好。工具返回也只保留必要字段，避免大量原文堆积。必要时用长上下文模型，但仍要关注成本、延迟和中间信息丢失问题。


## Q18: 已有向量库，为何不存储全部历史对话？

向量库适合语义召回，但历史对话有强时序性、结构化事实、最新状态和隐私权限等需求，全量向量化并不能高效支撑这些场景。原始对话进向量库会造成冗余、召回不稳定、权限生命周期难管理，也无法精确回答“刚才/上一步/某次操作”的时序问题。正确做法是：会话日志归档存储，向量库只存需要语义检索的知识片段或长期记忆；工作状态用结构化状态存储，最近上下文直接进短期记忆。


## Q19: 如何量化Agent任务完成率？工具成功率高等同于效果好吗？

任务完成率要按最终业务结果标注，例如“完成、部分完成、失败”，在离线评测集和线上抽样中由人工或 LLM judge 按明确成功标准打分。工具成功率高不等于效果好：模型可能调用了一个成功但与目标无关的工具，或者每个子步骤都成功但最终结果不可用。因此要同时看端到端指标：任务成功率、平均步数、耗时、token 成本、用户满意度、重试率和 Bad Case 率。分环节指标用于归因，但不能替代最终任务效果。


## Q20: Agent卡顿，如何定位模型、RAG、工具的性能瓶颈？

先做全链路埋点，记录每一步：LLM 首 token、推理 token 数、每个工具调用耗时、检索召回和 rerank 耗时、网络与排队时间。出现卡顿按 trace 定位耗时占比最高的阶段：模型慢看 TTFT/TPOT、上下文长度、是否高并发限流；RAG 慢看 embedding 延迟、召回数量、rerank 模型、索引性能；工具慢看下游 API、超时阈值和重试策略。优化时优先设置超时、并行、缓存，并对重链路做异步化；用分布式追踪把各段耗时串起来。
